- 撰寫：pm-planner，2026-09-12
- 嚴重度：**低（非阻擋性）**——效能計時測試脆弱性（flaky test），不影響任何遊戲機制或玩家體驗，但因 T-002 修好之前 `runtests.js` 的 exit code 誤判問題（見 `docs/tickets/T-002-測試斷言吞錯誤碼.md`），這類單獨執行、不經過 `runtests.js` 的 flaky 失敗有可能長期被忽略；建議排在 T-005／T-006 之後處理，不建議無限期擱置

## 1. 目標

讓 `tests/s22test.js` 第 54-58 行「模擬器速度：20 局 < 4 秒」這項計時斷言，在合理的環境效能變異範圍內**穩定**通過，不要繼續當一個「已知但被放行」的 flaky 失敗長期掛在測試清單裡。

## 2. 背景與根因（引用 release-manager 回報，已確認與 T-004 無關）

已讀 `docs/reports/T-004-release-manager.md` 與 `tests/s22test.js` 全文，核對如下：

- 斷言位置：`tests/s22test.js:54-58`
  ```js
  step("模擬器速度：20 局 < 4 秒（S21 乾跑版是 20 局 69 秒）",()=>{
    const t=Date.now();
    for(let g=0;g<20;g++){ const S=ns.sim.playOne(util.clone(cfg),mods,(31337+g*7919)>>>0,['NPC_SAFE','NPC_LEVER','NPC_VC','NPC_SAFE']);
      A(!(S.simStatus&&!S.simStatus.valid),"第 "+g+" 局跑壞："+(S.simStatus&&S.simStatus.reason)); }
    const ms=Date.now()-t; A(ms<4000,"20 局花了 "+ms+"ms"); return ms+"ms";
  });
  ```
  測試標題註解本身留了一條線索：「S21 乾跑版是 20 局 69 秒」，代表這條 4000ms 門檻是在某次效能優化（把 69 秒壓到 4 秒內）之後、比照當時的優化成果設下的絕對毫秒數，**沒有任何效能餘裕係數**。
- **release-manager 在 T-004 發布驗證時實測**：`npm test` 完整跑時此項 FAIL 兩次，分別量到 **5338ms**（3.1 節）與 **5219ms**（3.3 節）。
- **release-manager 已用 `git stash` 驗證過與 T-004 無關**：把工作區還原到 T-004 改動之前的基準版本（commit `5a06845`，即 `v2.53.0-S45`），重跑 `node tests/s22test.js`，**同樣 FAIL**（4136ms）。這證實了門檻過緊或環境變慢是既有問題，**不是 T-004 這次任何改動引入的回歸**。
- 可能原因（release-manager 回報中列出、本票沿用，尚未定案，需驗收條件 2、3 查證）：
  1. 執行測試的本機環境效能／負載跟當初設 4000ms 門檻時的基準環境不同（機器變慢，或當下同時有其他程式在跑）。
  2. 門檻本身設得太緊，沒有留任何效能餘裕係數。
  3. 或者模擬器本身在某次改動後（不確定是哪次）效能真的變差了，只是一直沒被抓到——因為 T-002 修好之前，`tests/runtests.js` 內部斷言失敗不會讓 `npm test` 的 exit code 非 0；雖然 `s22test.js` 本身有自己的 `process.exit(fail?1:0)`（獨立於 `runtests.js` 之外），理論上會讓鏈中斷並回傳非 0，但這類「跑一次剛好卡在邊界」的計時 flake，過去是否曾被人工略過、有沒有被真正正視過，本票查證範圍內需要一併確認。

## 3. 驗收條件（【AI】＝AI 可自驗；【本機】＝需製作人或 qa-tester 本機確認）

1. 【AI】**查證 4000ms 門檻的歷史依據**：用 `git log -p` 或 `git blame` 追蹤 `tests/s22test.js` 這一行斷言（含「S21 乾跑版是 20 局 69 秒」這句註解）是在哪個 commit／哪個 sprint 引入的，當時的 commit message 或對應的 changelog／任務單有沒有說明基準環境（例如測試機規格、當時實測的 ms 數）。查不到就在回報中明確標 UNKNOWN，不要編造。
2. 【AI 或 qa-tester，建議先做】**判斷是不是穩定重現**：在同一台機器上連續執行 `node tests/s22test.js` 至少 5 次（不要只跑一次就下結論），逐次記錄「20 局花了 Nms」的實際輸出。判斷：
   - 若多數次（例如 5 次中 ≥3 次）都超過 4000ms → 判斷為「持續性」問題，門檻與目前環境速度確實不合。
   - 若多數次都在 4000ms 內、只是偶爾超過 → 判斷為「偶發」，需記錄當次環境負載狀況（例如是否有其他程式同時在跑），但仍建議留一點餘裕，不要放著不管。
3. 【AI】依驗收條件 1、2 的查證結果，二選一（或先做 b 排除後再做 a），並在回報中寫清楚判斷依據，不要只憑「反正之前都過」帶過：
   - **方案 a（放寬門檻）**：若判斷是門檻本身沒有效能餘裕係數，加一個合理的餘裕（例如 4500ms 或 5000ms，需在回報中說明選這個數字的依據，例如「連續 5 次量測最大值 + 一定比例緩衝」），並更新測試檔內的註解，說明新門檻與依據（比照現有「S21 乾跑版是 20 局 69 秒」這種留歷史紀錄的寫法）。
   - **方案 b（查真正效能退化）**：若懷疑模擬器（`ns.sim.playOne`／engine 層）在某次改動後真的變慢，需要先做查證（例如用 `git blame`／`git log` 找出 `src/engine/` 下 `sim`／`playOne` 相關程式碼近期的改動時間點，比對改動前後版本的實測 ms 數），確認是否為真退化。**若確認是真退化，不要用放寬門檻掩蓋問題**——回報中明確指出可疑改動，並回頭升級給 architect／製作人決定是否要開額外的效能修復票（不在本票範圍內直接修效能）；若查證後排除是真退化（純粹環境變慢），才轉回方案 a。
4. 【AI】調整（或確認不調整）後，**連續執行 `node tests/s22test.js` 至少 3-5 次**，附上每次「20 局花了 Nms」的實際輸出，證明這項測試在新門檻下能穩定通過（不是跑一次剛好過）。
5. 【AI】完整跑一次 `npm test`（或至少 `npm run test:ui`），確認本次調整沒有讓其他既有測試項目多出新的 FAIL，附輸出與 exit code。
6. 【AI】若查證後結論是「維持 4000ms 不變」（例如判斷 release-manager 那次是單次環境負載偶發，且連續 5 次重測都在 4000ms 內），需在回報中明確寫出理由與佐證數據，不能只憑一次觀察就下結論維持原狀。

## 4. 建議分派角色

建議**先由 qa-tester** 查證驗收條件 1、2（歷史依據＋連續執行重現穩定性），確認這是「持續性門檐過緊」還是「這台機器當下負載偶發」；查證結果出來後，再依驗收條件 3 的判斷分支：
- 若走**方案 a**（單純調整門檻＋註解），改的是 `tests/`，qa-tester 本身即可完成，不一定需要換手給 engine-engineer。
- 若走**方案 b**（懷疑真退化，需要比對 `src/engine/` 下模擬器相關程式碼的歷史改動），因為模擬器效能屬於 engine 層，需要轉給 **engine-engineer** 接手查證與（若製作人／architect 同意擴大範圍）修復。

pm-planner 不代為決定最終走哪個方案，這是查證後才能定案的技術判斷。
