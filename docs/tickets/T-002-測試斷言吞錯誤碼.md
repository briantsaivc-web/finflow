# T-002 測試框架斷言失敗不會讓 `npm test` 回傳非 0

- 需求來源：QA（`docs/qa/T-001-qa-report.md` Bug #3／未預期發現 #2），製作人裁示 2026-09-10：開新票，不擋 T-001 收尾
- 撰寫：pm-planner，2026-09-10
- 嚴重度：**較急、較嚴重**——影響全專案所有未來版本的驗收判斷可信度，建議優先處理
- 目標版本：由 architect／release-manager 排入哪個 sprint，pm-planner 不指定

## 1. 目標
讓 `tests/runtests.js`（進而整條 `npm test`＝`test:engine && test:ui` 指令鏈）在**任何一個內部斷言失敗時**，shell exit code 都必須是非 0。目前的狀況是：`node tests/runtests.js` 內部跑 `ns.selftest.run(false)`，即使 97 項裡有 2 項 FAIL（T-68、T-86），該檔案仍然正常結束、exit code 是 0，導致 `npm test` 誤判為全過。

## 2. 背景與根因（已具體核對，非猜測）

已讀 `tests/runtests.js` 全文（27 行）與 `package.json` 的 `test`／`test:ui`／`test:engine` 指令鏈，並用 `Grep` 比對 `tests/` 目錄下所有 35 個測試檔案的 `process.exit` 用法。結論：

- **`tests/runtests.js` 是這條鏈裡唯一沒有依失敗結果呼叫 `process.exit` 的檔案。** 它在第 22–25 行印出結果與 FAIL 清單後，直接 `await b.close();` 收尾（第 25 行），**沒有任何一行讀 `out.pass`／`out.total`／`out.fails` 來決定 exit code**，所以 Node 行程照預設值以 0 結束——不管 `ns.selftest.run(false)` 回傳的 97 項裡有幾項是 FAIL。
- 相對地，其餘 34 個測試檔案（`s17test.js` ～ `s45test.js`、`editortest.js`、`gate.js`、`contentcheck.js` 等）**都已經**有 `process.exit(fail?1:0)`（或等效寫法）這一行——例如 `tests/s17test.js:100`：`process.exit(fail?1:0);`。這是專案裡既有、一致的慣例，**只有 `runtests.js` 漏掉**。
- `package.json` 的 `test:ui` 是用 `&&` 串起 30 個測試檔案（`node tests/runtests.js && node tests/s17test.js && ...`）。因為 `&&` 鏈裡第一棒 `runtests.js` 永遠回 0，所以鏈會照樣往下跑；即使後面 34 個檔案本身的 exit code 機制是對的，`runtests.js` 自己內部的斷言失敗永遠不會讓整條鏈失敗。
- 因此**不是**「指令鏈用了某種吞掉錯誤碼的寫法」（`&&` 本身是正確、會正常傳遞非 0 exit code 的），根因單純是 `runtests.js` 這一個檔案本身缺了 34 個兄弟檔案都有的那一行判斷式。

## 3. 驗收條件（【AI】＝AI 可自驗；【本機】＝需製作人或人工確認）
1. 【AI】`tests/runtests.js` 修改後：`ns.selftest.run(false)` 回傳結果中若有任一項 `ok===false`，該檔案以 `process.exit(1)` 結束；全部通過則 `process.exit(0)`
2. 【AI】**手動製造一個假的斷言失敗**（例如暫時在 `ns.selftest` 註冊的某個測試裡塞一個必定失敗的 `assert(false,"人工製造的假失敗")`，或暫時修改任一張卡片資料讓既有斷言失真），執行 `npm test`，確認：
   - shell exit code 非 0（`echo $?`／PowerShell `$LASTEXITCODE` 皆需附上實際輸出佐證）
   - 完成驗證後**還原**該人工製造的假失敗，不得留在程式或資料裡
3. 【AI】確認修好後、且 T-68（IPO_S20 卡片內容撞測試，QA Bug #1，非本票範圍）與 T-003（T-86 EXTEND_GAME，見另一張票）都已修復的前提下，完整跑一次 `npm test`，確認 exit code 為 0（即這次修正本身不能造成新的誤判、也不能讓原本會通過的情況變成誤報失敗）。**若驗收當下 T-68／T-003 尚未修好**，此條可改為：確認 `npm test` 的 exit code **正確反映**既有 2 項失敗（即回傳非 0），作為過渡驗證，並在回報中註明依賴尚未解除
4. 【AI】其餘 34 個既有測試檔案的 `process.exit` 寫法不受影響、不被誤改（僅動 `runtests.js`）
5. 【AI】確認 `package.json` 的 `test`／`test:ui`／`test:engine` 三個指令字串本身不需要更動（根因確認在 `runtests.js` 內部，而非 `&&` 串接方式），或若判斷需要調整也要在任務回報中具體說明理由

## 4. 建議分派角色（pm-planner 判斷，僅供參考，不代為分派）
- 這是**測試基礎設施的正確性修正**，改動範圍是 `tests/runtests.js` 一個檔案，修法是比照另外 34 個檔案已有的既有慣例（補一行 `process.exit(fail?1:0)` 等效邏輯），**不是新架構決策**——34/35 個檔案已經是一致先例，此票只是補齊最後一個漏網之魚，不需要為此開新 ADR。
- 依角色職責表，`tests/` 屬於 engine-engineer／ui-engineer／network-engineer 皆可改的共用目錄；`runtests.js` 呼叫的 `ns.selftest.run()` 是跨層級（涵蓋 engine 與 UI 的斷言，例如 T-86 屬引擎回合流程、T-68 屬 UI 內容掃描），沒有單一角色獨占。**建議直接指派 engine-engineer 或當前手上有 tests/ 空檔的角色即可動手**，改動本身簡單、風險低，不需要 architect 先審查（除非 architect 認為這類「測試框架一致性」問題值得順手寫一則簡短 ADR 存查，那是 architect 自行判斷，不是必要條件）。
- release-manager 不需要介入此票本身（不改版本號、不寫 changelog），但下一次版本發布前，release-manager 應確認這張票已收尾，避免帶著「測試框架會吞錯誤碼」這個已知問題發版。
