# T-005 真人決策卡在「電腦回合」下可能完全消失（既有潛伏缺陷，非 T-004 新造成）

- 需求來源：architect 於處理 T-004 時查證發現（`docs/adr/ADR-001-新股抽籤-T004補充裁決2.md`），製作人裁示 2026-09-11：開新票追蹤，不擋 T-004 收尾
- 撰寫：pm-planner，2026-09-11
- 嚴重度：**中（潛伏／低機率，但一旦命中，單機會靜默清空真人決策、多人無法自行恢復）**——不急著搶在 T-004 之前處理，但必須在 T-004 S3 完成後立刻補驗證，否則這個既有缺口會繼續留在程式碼裡不被任何測試覆蓋
- 目標版本：由 architect／release-manager 排入哪個 sprint，pm-planner 不指定
- 前置依賴：**本票的驗收條件全部依賴 `docs/tickets/T-004/dispatch.md` 的 S3（ui-engineer 修法 A／B／C）先完成**，見下方「交叉影響」

## 1. 目標

T-004 修好的三處 UI 根因（`ui.renderCenter` 判斷順序、`ui.tick` 守門、`T-59` 測試模擬迴圈）理論上是通用修復，不只是為了 `IPO_ANNOUNCE`。本票要做的是：

1. 針對既有機制 `STOCK_GAIN`（不是 IPO）明確補一個回歸測試，證明 T-004 的修法對它也真的生效，不是只驗證了 IPO 這一條路徑。
2. 把這個「真人決策卡在電腦回合下會被 `ui.renderCenter`／`ui.tick`／`showStuck` 降級流程靜默清空」的既有架構缺口記錄下來，供未來排查任何「玩家說某張卡突然消失」的類似回報時，第一時間就能對到根因，不用重新查一次。
3. 盤點還有沒有其他既有機制用同一種「`S.players.forEach` 對全場真人推播決策、不看現在輪到誰」的寫法，列出風險清單（不要求本票全部修）。

## 2. 背景與根因（引用既有查證文件，不自行推論）

完整技術細節見 `docs/adr/ADR-001-新股抽籤-T004補充裁決2.md`「查證 1～4」與「未預期發現」段落，以下只摘要三個連鎖點：

1. **`ui.renderCenter`（`src/ui/uiCore.js` 約 1835-1888 行）**：判斷「當前回合是不是電腦」（`p.isNPC`，第 1870 行）寫在判斷「決策卡歸屬」（`S.phase==="DECISION"`，第 1879 行）之前。只要當前回合是電腦，畫面一律卡在「NPC 思考中…」，`S.pendingDecision` 屬於哪一位真人完全不影響這個判斷順序，真人看不到自己的決策卡。
2. **`ui.tick`（`src/ui/uiViews.js` 約 734-767 行）**：NPC 自動回合驅動迴圈唯一的安全門 `E.waitingOnHumans`（`src/engine/reducer/applyAction.js:59-79`）只認得 `pendingAuction`／`pendingReferral`／`pendingJV`／`pendingTrade` 四種，不認得 `S.pendingDecision`。當前回合是電腦、但決策屬於別人時，迴圈仍會硬闖著幫電腦想動作，連續被引擎拒絕 8 次後觸發 `ui.showStuck()`（`uiViews.js:777-830`）。
3. **降級流程（`uiViews.js` 約 814-823 行）**：單機局玩家按「跳過這一位，繼續玩」時，執行 `S.decisionQueue=[]; S.pendingDecision=null;`，把懸置中、真人根本沒機會看到的決策卡**連同其他排在後面的決策卡一起靜默清空**。多人局則只能「重新同步這一局」，但狀態沒變，回去仍是同一個卡住的畫面，無實質解法。

**根因層級**：`S.phase==="DECISION"` 只看 `decisionQueue` 是否有東西（`E.syncPhase`，`src/engine/core/engineCore.js:1384-1391`），跟「現在輪到誰」（`S.activePlayerIdx`）完全無關——這是既有架構設計本身，不是 T-004 這次改動造成的。

**既有同款風險點（已確認、非本票新發現）**：`STOCK_GAIN`（帳上獲利達門檻提示，`src/engine/npc/contentNpcSim.js:103-116`）用的是完全相同的「`S.players.forEach` 對所有真人推播決策，不管現在輪到誰」寫法，且掛在 `onRoundEnd`（`contentNpcSim.js:74`，M1 股市引擎模組，價格更新後對全場結算，跟輪到誰無關），理論上有一模一樣的風險。它從未被踩到或回報過的原因是：觸發條件依賴真人**主動買股**且獲利達門檻，機率極低；`IPO_ANNOUNCE`（T-004）則是「新股到期即自動觸發，不需要玩家做任何動作」，才把命中率大幅拉高、被製作人實機踩到。

**pm-planner 本次額外查證（`Grep "E.pushDecision"` 全專案 `src/` 逐一核對呼叫情境，非猜測）**：除了 `STOCK_GAIN` 與 `IPO_ANNOUNCE`，`src/engine/` 內其餘所有 `E.pushDecision` 呼叫點都**只在被推播對象自己的回合內**觸發，理由如下，供之後排查時直接參考、不用重查：
- `E.tickDirectorship`／`E.tickDelistWarn`／`E.tickFutCall`／`E.tickRenewals`／`E.tickScamInvestments` 等（`src/engine/reducer/applyAction.js:4291-4295`）全部在 `E.beginTurn` 內、只對**即將開始回合的那一位玩家 `p`** 呼叫，程式碼註解本身就寫明「在自己的回合才跳卡」。
- `FOLLOW_ON`（新創跟投，`contentNpcSim.js:235`）掛在 `onPayday`（M3 模組），`onPayday` 只在 `E.payday(S,p)` 內被呼叫（`applyAction.js:4281`），而 `E.payday` 只在 `E.beginTurn` 對當前回合玩家呼叫，同樣是「只對自己回合的當事人推卡」，不是 forEach 廣播。
- 其餘呼叫點（`BUY`／`ACK`／`PICK_OPP`／`LIFESTYLE` 等）都是玩家親自觸發（踩格、抽卡）當下對觸發者本人 `p` 推卡，不涉及 forEach 廣播其他玩家。
- **只有 `onRoundEnd` 掛的 `STOCK_GAIN`（`contentNpcSim.js` M1 模組）與 `E.openIpo` 的 `IPO_ANNOUNCE`（`applyAction.js:4653-4656`，T-004 新增）是「觸發時機與被推播者的回合脫鉤」的 forEach 廣播寫法。** `contentNpcSim.js` 另外兩處 `onRoundEnd`（M4 總經模組 `applyInflation`/景氣轉換，M9 加密貨幣模組）內沒有任何 `pushDecision` 呼叫，不受影響。

結論：**目前已知、且會被 T-004 的三處修法一併修到的既有風險點只有 `STOCK_GAIN` 一個**，不是「一大片」，但仍值得記錄，因為 T-004 的三處修法本身是通用的渲染／驅動邏輯修復，不是針對 `IPO_ANNOUNCE` 寫死的 if 分支——這代表這次修復的效益比 T-004 任務單原本描述的範圍更廣，值得讓後續維護者知道。

## 3. 驗收條件（【AI】＝AI 可自驗；【本機】＝需製作人或人工確認）

**前提：以下條件必須在 `docs/tickets/T-004/dispatch.md` S3（ui-engineer 修法 A／B／C）完成、且 T-004 S4（engine-engineer 重跑 `npm test` exit 0）確認之後才能執行，見「交叉影響」。**

1. 【AI】在 `tests/` 內針對 `STOCK_GAIN` 情境（不是 IPO）新增至少一項回歸測試，情境需包含：混合局（≥1 真人＋≥1 電腦），真人持股獲利達 `stockGainAlertPct` 門檻、`onRoundEnd` 觸發 `STOCK_GAIN` 推卡的當下，`S.activePlayerIdx` 恰好指向一位**電腦**玩家（不是持有該決策卡的真人）；斷言：
   - 真人的 `S.pendingDecision` 正確存在且 `kind==="STOCK_GAIN"`、`playerId` 是該真人
   - 比照 `T-59`（`uiViews.js` 死當重現迴圈）修法 C 的模式，真人可以在非自己回合送出 `DECIDE` 解掉這張卡，不被引擎拒絕
   - 不觸發 `ui.showStuck()`（或等效的「卡住了」降級路徑），`decisionQueue` 不被靜默清空
2. 【AI】跑 `node tests/runtests.js`，確認新增測項 PASS，且既有全部項目（含 T-004 修好後應為 97/97 的 `T-59`）不因本次新增測試而新增任何 FAIL
3. 【AI】跑完整 `npm test`，確認 exit code 0（沿用 T-004 S4 的驗證基礎，不需要重新驗證 T-004 本身，只需確認本票新增內容不破壞既有綠燈）
4. 【AI】回報中需明確引用本票「2. 背景與根因」段落列出的 `E.pushDecision` 全面盤點結果（或執行者自行重新 `Grep` 覆核後的結果），若發現 pm-planner 本次盤點有遺漏或过时（例如之後又新增了其他 forEach 廣播式 `pushDecision`），需在回報中列出、並說明是否也需要同款回歸測試（不要求本票一併修，只要求記錄）
5. 【本機】qa-tester 或製作人在單機局手動重現一次「電腦回合中，真人因 `STOCK_GAIN` 收到決策卡」的情境（可用測試 seed 或人工加碼觸發門檻），確認畫面正確顯示決策卡、不是「NPC 思考中」卡死，也不會被「跳過這一位」按鈕靜默清空

## 4. 建議分派角色（pm-planner 判斷，僅供參考）

- **engine-engineer 或 ui-engineer** 均可承接，判斷依據：本票新增的測試同時涉及 `contentNpcSim.js`（`STOCK_GAIN` 觸發條件建局，engine 領域）與驗證「真人可在非自己回合解卡」這條路徑是否正確運作（依賴 T-004 S3 已經修好的 `uiCore.js`／`uiViews.js`，UI 領域），但測試本身如果比照 `T-59` 修法 C 的寫法（直接呼叫 `E.apply` 模擬，不經過真實 DOM 渲染），落在 `tests/` 目錄，兩個角色的可改範圍都涵蓋 `tests/`。**建議優先指派剛完成 T-004 S3 的 ui-engineer**，因為對 `ui.renderCenter`／`ui.tick`／`T-59` 三處修法的最新狀態最熟悉，銜接成本最低；若排程上 ui-engineer 沒空，engine-engineer 接手也可行，只是需要先重讀一次 ADR 補充裁決 2 的三處修法內容。
- 不需要 architect 重新裁決或另開 ADR——本票的修法性質是「照抄 T-004 已裁決通過的修法，換一個既有情境（`STOCK_GAIN`）驗證」，不是新架構決策。

## 6. 風險

- 若 T-004 S3 的三處修法（A／B／C）在實作時與 ADR 補充裁決 2 描述的行號或邏輯有出入（例如本機有其他未合併修改），本票的驗證會直接暴露落差——這是預期中的效果，不是本票的風險，是本票存在的價值之一。
- 本票的「全面盤點」（第 2 節）是 pm-planner 用 `Grep` 靜態核對，**不是動態執行驗證**，理論上仍有極小機率漏掉某個透過間接呼叫（例如透過 `M.registry` fanout、或字串拼出函式名再呼叫）繞過 `Grep "E.pushDecision"` 直接比對的字面呼叫寫法。執行者若在補測試過程中發現本票列出的清單有遺漏，依驗收條件 4 需要記錄回報，不要求本票一併修。
- 這個問題目前**沒有任何已知的實際玩家事故回報**（是 architect 主動查證發現，不是 QA 或製作人先踩到才回報），嚴重度定為「中」而非「急」，不建議插隊搶在其他進行中票之前處理，但也不建議無限期拖延——T-004 S3 完成後應盡快排入，避免這個既有缺口在下一次類似情境（例如未來新增的其他跨玩家推播機制）又被重新踩到卻找不到已有的根因記錄。
