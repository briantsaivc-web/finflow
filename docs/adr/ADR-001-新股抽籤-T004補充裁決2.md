# ADR-001 補充裁決 2：T-004 卡住——`ui.renderCenter` 的渲染順序本身有真實 bug，不只是測試沒覆蓋

- 對應：T-001（ADR-001）／T-004
- 觸發：engine-engineer 完成 S1（`E.openIpo` 廣播給全場真人）後回報 `docs/reports/T-004-engine-engineer.md`，`npm test` 非 0，要求 architect 裁決兩個問題
- 裁決者：architect
- 日期：2026-09-11
- 狀態：**通過（裁定：engine 端 S1 的設計方向維持不變，但在 UI 端完成本文件列出的修復並驗證前，T-004 不能算完成／不能上線）**

## 背景（讀碼覆核，逐項附行號，不是推論）

engine-engineer 的回報指出：`T-59`（`src/ui/uiViews.js:5464-5552`）的死當重現模擬迴圈，只有在「當前回合玩家是那位持有 pendingDecision 的真人」時才會處理 `DECIDE`；當前回合是電腦、但 pendingDecision 屬於另一位真人時（本次 T-004 修法後的合法情境），這條迴圈完全沒模擬「真人在非自己回合解掉自己的懸置決策」，於是新增一項 FAIL：「電腦回合連 END_TURN 都被拒」。ADR 補充裁決文件 1 當時的 lockstep 風險評估判斷這是既有的 `STOCK_GAIN` 同款、已上線行為，不是新風險——**這個判斷在「lockstep 確定性」層面沒錯，但在「真實 UI 是否真的會正確運作」這件事上，沒有查證就下了結論。本次查證的結果是：不會正確運作，是真的會卡住，而且卡住之後的降級流程會把真人的決策靜默清空，比原本的 bug 更糟。**

### 查證 1：`ui.tick`（NPC 自動回合驅動迴圈，`src/ui/uiViews.js:734-767`）

- 第 736-737 行：`var p=E.activePlayer(ui.S); if(!p.isNPC) return;`——只在**當前回合玩家**是電腦時才會啟動這個迴圈。
- 第 742-743 行：`var wOn = E.waitingOnHumans(ui.S); if(wOn && wOn.waiting && wOn.waiting.length){ ui._stall=0; ui.render(); return; }`——這是目前唯一會讓這個迴圈「安靜停下來」的守門機制。
- 但 `E.waitingOnHumans`（`src/engine/reducer/applyAction.js:59-79`）只認得 `S.pendingAuction`／`S.pendingReferral`／`S.pendingJV`／`S.pendingTrade` 四種，**完全沒有檢查 `S.pendingDecision`**。
- 結論：當前回合是電腦、但 `S.pendingDecision` 屬於另一位真人時，`wOn` 是 `null`，這個守門機制完全不會擋下來。迴圈會照樣呼叫 `ns.npc.nextAction(ui.S)` 幫電腦想動作，因為 `S.phase==="DECISION"`（見下一段 `E.syncPhase`），這個動作與其 `END_TURN` 後備都會被引擎拒絕（`T-59` 新增的 FAIL 就是這個真實行為，不是測試自己造出來的假象）。連續 8 次沒有前進（`ui.tickSig()` 不變）後，觸發 `ui.showStuck()`（`uiViews.js:777-830`）。

### 查證 2：`E.syncPhase`（`src/engine/core/engineCore.js:1384-1391`）

```
S.pendingDecision = S.decisionQueue.length ? S.decisionQueue[0] : null;
if(S.pendingDecision){ S.phase = ... "DECISION"; return; }
```
`S.phase==="DECISION"` 只看 `decisionQueue` 是否有東西，**跟 `S.activePlayerIdx`（現在輪到誰）完全無關**。而 `E.endTurn`（`applyAction.js:4221-4230`）是先把 `S.activePlayerIdx` 往下一位推進、輪到 0 才呼叫 `E.onRoundEnd`（`STOCK_GAIN` 等 forEach 推播都在這裡發生）——也就是說，**「當前回合玩家是電腦、但決策屬於另一位真人」這個組合在架構上本來就會發生，不是 T-004 新引入的狀態，只是 T-004 讓它從「低機率」變「常態」。**

### 查證 3：`ui.renderCenter`（`src/ui/uiCore.js:1835-1888`）——真正的核心 bug，比 `ui.tick` 更嚴重

這是本次查證最重要的發現，**T-004 engine-engineer 的回報沒有查到這一層，因為那是 UI 渲染邏輯，不是他能跑的引擎測試**：

```js
var p=E.activePlayer(S);                 // 1841：當前"回合"玩家，跟決策擁有者無關
...
if(p.isNPC){                              // 1870：只要現在輪到電腦……
  ...思考中... return;                    // 1875：……就在這裡直接 return
}
if(S.phase==="DECISION" || S.phase==="BANKRUPTCY"){   // 1879：這裡永遠到不了
  var dOwn = S.pendingDecision;
  var dp = ... S.players[dOwn.playerId] ...;          // 1884-1885：本來就是找「卡的擁有者」
  ui.modalOn(true); ui.decisionCard(S,dp,dOwn); return;
}
```

**`p.isNPC` 的判斷（用的是「現在輪到誰」）被放在 `S.phase==="DECISION"` 的判斷（用的是「決策卡的擁有者是誰」）前面。** 只要當前回合玩家是電腦，不管 `S.pendingDecision` 是不是屬於正在看這個畫面的真人，畫面一律卡在「NPC 思考中…」，**1879 行那段原本就寫對的「用擁有者的資料畫卡」邏輯完全走不到**。

這代表：T-004 修法之後，電腦觸發 IPO 開盤、決策卡推給真人，只要當下剛好輪到另一位電腦，真人自己的畫面上**根本看不到自己的決策卡**——不是「弱通知」，是**完全沒有 UI 入口**。跟 T-59 死當重現的結果完全對得上，不是測試孤立的假象，是會在真實遊戲裡發生的行為。

### 查證 4：卡住之後會發生什麼——單機比原 bug 更糟，多人無解

- 單機（`!ui.mp.mode`）：`ui.tick` 連續 8 次撞牆後，`ui.showStuck()` 顯示「⚠ 卡住了」，玩家唯一能按的鈕是「跳過這一位，繼續玩」（`uiViews.js:814-823`），其效果是：
  ```js
  S.decisionQueue=[]; S.pendingDecision=null; S.bookkeeping=null; S.turnResolved=true;
  E.syncPhase(S);
  var r=E.apply(ui.S,{type:"END_TURN",...});
  ```
  **直接把整個 `decisionQueue` 清空**——真人的 `IPO_ANNOUNCE` 決策連同其他任何排在後面的決策卡，一律被靜默丟棄，真人從頭到尾沒有機會看到、更不用說回應。這比製作人原本回報的「完全沒有選單跳出來」還糟：原本至少交易所列與 toast 還在，玩家可以自己去交易所手動申購；現在這個決策卡被引擎排入佇列、卻在 UI 層被強制清空，連被動管道都一起沒了。
- 多人（`ui.mp.mode`）：`ui.showStuck()` 唯一選項是「重新同步這一局」，即從房間紀錄重新載入（`uiViews.js:808-811`）。但重新載入後，`S` 的狀態（`decisionQueue`、`activePlayerIdx`）跟卡住前完全一樣，`ui.renderCenter` 的渲染順序 bug 沒有被修掉，**重新同步只會回到同一個卡住的畫面，沒有實質解法**。

### 結論（回應主對話問題 1 的三點）

1. 真實 UI 的 NPC 自動回合驅動邏輯（`ui.tick`）**不會**正確停下來等真人解卡——它會先撞牆 8 次才觸發降級處理，而不是一開始就安靜識別「這是在等別人的決策」。
2. 這條路徑（電腦回合中，另一位真人有懸置決策）在正式版**目前無法正常運作**：核心問題出在 `ui.renderCenter` 的判斷順序，這個 bug **不是 T-004 新引入的**，`STOCK_GAIN` 理論上早就有同樣的風險，只是觸發條件（真人主動買股又剛好在回合尾聲達門檻、且下一個活躍玩家剛好是電腦）機率低到至今沒人踩過、也沒被任何測試覆蓋過。T-004 把 IPO 開盤（不需要真人任何主動行為、到期即觸發）跟這個 bug 疊在一起，讓命中率大幅提高。
3. **⚠️ 需要重新評估——但評估結果是：不是要 revert engine 端的改動，而是要把「這是一個完整功能」的定義擴大到包含 UI 修復。** `E.openIpo` 廣播給全場真人這個設計本身是對的（架構、lockstep 都沒問題，也有 `STOCK_GAIN` 先例），問題出在 UI 層一個獨立、既有、原本潛伏的 bug 被它引爆。真正的替代方案（例如改回「只推給觸發者」或「輪到自己才推」）都不能解決 `ui.renderCenter` 的根因，只是把命中率壓回低，讓同一個 bug 換個時間點再爆——**不採用縮小範圍的替代方案，採用「先修 UI 根因，再放行」。**

## 決策：三處具體修法，全部在 `src/ui/` 與其對應測試內，不動 engine

### 修法 A（根因，必須做）：`src/ui/uiCore.js`，`ui.renderCenter`（1835-1888 行）調整判斷順序

### 修法 B（避免誤觸發卡住畫面，必須做）：`src/ui/uiViews.js`，`ui.tick`（734-767 行）加一道守門

只做修法 A，`ui.tick` 仍然會在「當前回合是電腦、決策屬於別人」時空轉 8 次才安靜下來（因為 `E.waitingOnHumans` 不認得 `pendingDecision`）。這 8 次都會被 `E.apply` 拒絕，執行成本很低，正常情況下不會被玩家看到（`ui.render()` 在修法 A 之後已經正確顯示決策卡），但仍會在 8 次之後誤觸發 `ui.showStuck()`——一個原本不該出現的「卡住了」假警報，且其「跳過這一位」按鈕會照樣清空決策佇列，摧毀掉修法 A 剛救回來的東西。**必須同時擋掉，不能只做 A。**

## 給 ui-engineer 的執行順序

1. 先做修法 A（`uiCore.js`），再做修法 B（`ui.tick`），最後做修法 C（`T-59`）——A／B 是同一個根因的兩面（渲染端＋驅動端），必須都做才能讓 C 的測試真正驗到「修好之後」的行為；C 如果先做、A／B 沒做，`node tests/runtests.js` 還是會 FAIL（因為 T-59 的新分支模擬的是「真人可以解卡」，但 (a) 段的不變式掃描本來就沒問題，是 (b) 段的死當重現本身依賴 A／B 修好後的引擎行為才會通——不過(b)段是直接呼叫 `E.apply`，不經過 UI render，所以理論上只要 C 自己補的分支邏輯正確，不修 A／B 光做 C 也能讓 `T-59` 本身變綠；**但這樣只是讓測試通過，沒有真的修好 UI，之後製作人實機還是會卡住**——三個修法都要做，這是同一張票的完整交付，不是三選一）。
2. 三處都改完後，順便修問題 2 的 fixture（見下方，同樣在 `tests/s45test.js`，同一輪一起做）。
3. 完成後回報 `docs/reports/T-004-ui-engineer.md`，附三處 diff＋`node tests/runtests.js` 全數輸出＋`node tests/s45test.js` 全數輸出（S1＋S2 都要跑，確認 S1 的 19 項與 S2 的 5 項全綠）。

1. 註解「0 號真人……其餘電腦」與 `s39test` 同款佈置的既有意圖，本來就是**單一真人**——這是這五項 S2 測試（IPO 決策卡顯示、申購小資檔、都不要、交易所列、訊息欄）全部共用的建局基礎，它們驗證的是「單一真人在自己畫面上跟 IPO 決策卡互動」這件事本身的 UI 正確性，不是在測「多真人各自收卡、互不干擾」——那件事已經由 `D5-1c（T-004）`（engine-engineer，S1）在引擎層完整覆蓋掉了，S2 沒有必要也重複驗證一次。
