# ADR-001 補充裁決：T-004（新股公告——電腦觸發時真人完全收不到跳卡）

- 對應：T-001（ADR-001）／T-004
- 觸發：製作人 2026-09-11 實機遊玩回報——第 14 輪出現「📢 新股申購開放」公告，沒有任何選單跳出來，第 15 輪直接結算成 0 筆申購、中籤 0 筆
- 裁決者：architect
- 日期：2026-09-11
- 狀態：**通過（裁定方向：擴大 `E.openIpo` 的跳卡對象，從「只有觸發者」改成「全場還在場、沒破產的真人」）**

## 背景（不重複主對話的排查全文，只列裁決依據與新增證據）

主對話已用讀碼排查出兩條路徑：①觸發者是真人 → 理論上決策卡會正常跳出；②觸發者是電腦 → 其他真人完全沒有主動通知，只能自己跑去交易所畫面手動點。裁決前我做了兩件事：讀碼覆核＋寫一次性 node/Playwright 腳本直接呼叫 `E.openIpo` 驗證，不是純讀碼推論。

### 驗證結論（逐項回應主對話的問題 1）

1. **①真人觸發路徑：讀碼判斷正確，且有既有自動化測試佐證**——`tests/s45test.js` 的「D5-1：真人踩到 MARKET 格」與「D5-1b：電腦踩到 MARKET 格」兩項已跑過，全數 PASS（`node tests/s45test.js` 輸出 `{"pass":18,"fail":0,"pageErrors":0}` 與 `{"pass":5,"fail":0,"pageErrors":0}`，本次重跑無回歸）。真人自己觸發時，`E.openIpo`（`applyAction.js:4639-4650`）目前就會 `E.pushDecision`，`E.apply` 結尾無條件呼叫 `E.syncPhase`（`applyAction.js:1556`／`engineCore.js:1384-1387`）把它設成 `S.pendingDecision`，UI `d.kind==="IPO_ANNOUNCE"` 分支（`uiCore.js:2659`）渲染正常。**這條路徑沒有 bug。**

2. **②電腦觸發路徑：主對話的判斷方向正確，但「完全沒有被動或主動通知」這句話不準確，需要修正**——實際上已經有兩層被動通知，只是都偏弱：
   - `uiViews.js:391-393`：`IPO_OPENED` 事件處理，非觸發者會收到 `ui.toastSys("📢 新股申購開放，交易所可以看",...)`，這是**真實存在的 toast**，`ui.dispatch`（`uiViews.js:101-118`）在同一次同步呼叫裡跑 `E.apply→ui.handleEvents→ui.render`，所以電腦自動回合觸發時，這個 toast 會在真人畫面上**即時**跳出，不是要等真人自己去翻訊息欄才看得到。
   - `uiCore.js:932-948`：交易所「📢 新股申購中」列。這一段**不是**獨立畫面／分頁，是 `ui.renderFinBoard`（每次 `ui.render()` 都會跑，`uiCore.js:342`）畫在主看板中欄（`#infoM`）裡的一個小節，跟總經訊息、系統訊息、股市資訊同一頁並排，不需要切換畫面即可看到；`tests/s45test.js`「交易所『📢 新股申購中』列」一項也已驗過存在與可點擊。

   但這兩層通知在實務上確實**弱到幾乎等於沒有**：
   - toast 只顯示約 4 秒（`ui._showToast`，`uiCore.js:104-109`，`ms||2200`，這裡帶的是 4000），電腦回合是自動連續播放的（`uiViews.js:767` 的 `npcTurnMs` 節奏），如果連續好幾位電腦玩家的回合緊接在後面觸發其他事件的 toast，這一則很容易被後面的 toast 洗掉、或玩家當下沒在看螢幕就錯過，之後不會重播。
   - 交易所那一列是**非阻塞、非強制**的資訊列，混在同一欄其他一堆資訊（P2P、合資、總經、系統訊息）裡，沒有任何機制強迫玩家在自己的回合裡去注意它。

   **結論：主對話的核心判斷（電腦觸發時，真人容易在完全沒被強制提醒的情況下錯過整個機制）成立，只是措辭「完全沒有被動或主動通知」要修正為「有通知，但通知層級是非阻塞、易被忽略的被動訊息，不是強制決策」。**

3. **有沒有我沒發現的其他推播機制？沒有。** 我用讀碼＋一次性驗證腳本確認：`S.ipo.pending` 存在期間，除了上述 toast＋交易所列，唯一會把玩家「攔下來」的機制只有 `IPO_ANNOUNCE` 決策卡，而它只在 `E.openIpo` 對觸發者本人推（`applyAction.js:4649` 原碼 `if(!p.isNPC) E.pushDecision(S,p,{...})`）。我另外用一次性腳本直接呼叫 `E.openIpo(S, npcPlayer)`（4 人局、玩家 0 是真人、玩家 2 是電腦，其餘電腦）驗證：
   ```
   （現況）單真人局，NPC(2)觸發 openIpo 後 decisionQueue = []
   ```
   **`decisionQueue` 是空的。** 這證實了：只要觸發者是電腦，真人這局完全不會收到任何一張決策卡——這正是製作人回報「沒有任何選單跳出來」的根因，不是我推論出來的，是直接跑程式碼觀察到的結果。

## 裁決：擴大跳卡對象（主對話選項 (c) 的精簡版）

### 為什麼不選 (b)（延長結算視窗）
只延長視窗不會讓玩家「注意到」，只是讓弱通知的曝光時間變長，治標不治本，而且會讓 `ipoGraceTurns`／結算時機的既有語意複雜化（要處理「視窗延長期間又有下一檔排定到期」之類的邊界）。**不採用。**

### 為什麼選 (c)，但用「開盤當下一次跳給所有人」而不是「各自回合開始才跳」
主對話原文的 (c) 是「輪到自己的回合開始才跳卡」。我改成**開盤那一刻，同步跳給全場還在場、沒破產的真人**，理由：

1. **有現成、已經上線在跑的精確先例**，不是新發明：`contentNpcSim.js:103-116` 的 `STOCK_GAIN`（帳上獲利達門檻提示）就是 `S.players.forEach` 對**所有**真人（不分是否輪到他）同時 `E.pushDecision`，`uiCore.js:1880-1886` 也明文寫了「決策卡的主體必須是決策的擁有者，不是當前回合玩家」，就是為了處理這種「決策可能屬於別人」的情況。照抄這個模式，風險最低、程式碼量最小。
2. **「輪到自己才跳」在多人局裡一樣可能拖到一整輪才輪到某位真人**，跟現在的問題（結算視窗只有一輪）在覆蓋率上沒有本質差異，只是把「有沒有跳卡」的時間點往後挪；**開盤當下就跳**才是唯一保證「這一局只要真人還在場，就一定會被通知到」的做法。
3. 單機（一真人＋多電腦，也是製作人回報的場景）下，這個改法等於「不管是誰踩到 MARKET 格或觸發保底，真人畫面上一定會立刻跳出決策卡」，**直接、完整**地修掉製作人回報的現象，不需要任何額外的「輪到自己才生效」邏輯去判斷時機。

### 具體改法（可直接動手，不用再回來問）

**只改 `src/engine/reducer/applyAction.js` 的 `E.openIpo`（目前在 4638-4650 行附近，行號可能因本地其他未合併修改而略有偏移，用函式名定位）：**

現況最後一行：
```js
if(!p.isNPC) E.pushDecision(S,p,{ kind:"IPO_ANNOUNCE", ipoId:id });
```

改成：
```js
// T-004：不只是觸發者——全場還在場、沒破產的真人都直接跳卡，不再只靠交易所被動列＋toast。
// 比照既有 STOCK_GAIN（contentNpcSim.js:103-116，onRoundEnd 對所有真人跳卡）的既定作法：
// 決策卡各自獨立掛在 decisionQueue 上，擁有者各自是 S.pendingDecision.playerId，
// 不受「現在輪到誰」限制（uiCore.js:1880-1886 既有規則），FIFO 逐一跳出、互不干擾。
S.players.forEach(function(q){
  if(q.isNPC || q.bankrupt) return;
  E.pushDecision(S, q, { kind:"IPO_ANNOUNCE", ipoId:id });
});
```

不動 `E.ipoPollNPC`、`E.settleIpo`、`E.ipoDue`、D3/D4/D6/D7 任何一段。這是**唯一需要改的地方**——`E.openIpo` 是 MARKET 格觸發（D5-1）與保底觸發（D5-2）共用的同一個函式，改這裡兩條觸發路徑都會生效，不需要在 `case "MARKET"` 或 `E.beginTurn` 的保底區塊另外加邏輯。

### 我已經跑過的驗證（不是空談，附實際輸出）

用一次性 Playwright／node 腳本（未提交進 repo，跑在本機 `index.html`）直接 monkeypatch `E.openIpo` 成上面的邏輯，重跑相同情境：

```
（現況，未修）單真人局，NPC(2)觸發 openIpo 後 decisionQueue = []
（修法後）單真人局，NPC(2)觸發 openIpo 後 decisionQueue = [IPO_ANNOUNCE:0]
（修法後）雙真人局(0,1)，NPC(3)觸發後 decisionQueue = [IPO_ANNOUNCE:0, IPO_ANNOUNCE:1]
  P0 送 IPO_DECLINE 後：ipo.declined={"0":true}
  P0 送 DECIDE 收卡後 decisionQueue = [IPO_ANNOUNCE:1]（P1 的卡不受影響）
（現況，未修）單真人局，真人(0)自己觸發 decisionQueue = [IPO_ANNOUNCE:0]（既有行為，維持 1 張，不受影響）
```

確認：①單真人局下，電腦觸發後真人保證收到卡（直接修掉回報的 bug）；②雙真人局下，兩人各自收到各自的卡，一人解掉不影響另一人（FIFO、ownership 都正確，`DECIDE` 的 `NOT_YOUR_DECISION` 守衛見 `applyAction.js:324-325`）；③真人自己觸發、全電腦局（`tests/s45test.js` 既有的 D5-1／D5-1b／整合測試場景）行為完全不變，不會回歸。

也跑過完整 `node tests/s45test.js`（改動前，作為 baseline）：`{"pass":18,"fail":0,"pageErrors":0}` 與 `{"pass":5,"fail":0,"pageErrors":0}`，全數通過，證實現有 18＋5 項斷言的建局方式（`mk(seed,allNpc,...)`）沒有一項會因為這個改動被破壞——D5-1b 用的是全電腦局（`allNpc=true`，連 player0 都是電腦），`forEach` 會把所有人濾掉，`decisionQueue.length===0` 的既有斷言不受影響；D5-1 用的是預設局（只有 player0 真人），`forEach` 只會推 1 張卡給 player0，跟原本 `if(!p.isNPC)` 的結果一致。

## lockstep 風險評估（回應主對話問題 3）

**風險：低，不需要另外經 architect 二次確認、不需要新開 ADR 例外。**

- `S.players.forEach` 是走**固定順序的陣列**（座位序，建局時就決定，不是 `Object.keys` 那種會受物件插入順序影響的寫法），跟 T-003 補充裁決文件裡對 `E.ipoPollNPC` 的既有結論（`ADR-001-新股抽籤-T003補充裁決.md` 第 144-158 行）是同一類判斷。
- 判斷條件只有 `q.isNPC`、`q.bankrupt`，都是**已經在 state 裡、非回合當下才決定**的欄位，不讀 `Date.now()`、不讀 `Math.random()`、不讀 DOM、不讀任何全域可變狀態。
- `E.pushDecision` 本身（`engineCore.js:1379-1383`）只做 `decisionQueue.push`＋`util.uid(S,"d")`（`uid` 的計數器是 state 內部的遞增序號，非時間戳，所有客戶端重放同一個 action 序列會得到一致的 `decisionId`）。
- 這個改動只是把「該不該推」的判斷範圍從「一個人」擴大成「forEach 全部真人」，沒有新增任何隨機性或跟執行環境相關的分支，`E.openIpo` 本身早已在 ADR-001「影響」段落標記 lockstep ☑，這次改動不改變這個結論。
- 多人連線下的行為差異：現在 `S.phase==="DECISION"` 會因為任何一位真人（不限當前回合者）有懸置的 `IPO_ANNOUNCE` 而全桌暫停，直到那位真人在**他自己的裝置**上解掉——這個模式跟現有 `STOCK_GAIN` 完全一樣，是**既有、已經上線在跑**的多人行為模式，不是這次新引入的風險。但這次改動會讓「全桌因為別人的決策卡而暫停」發生的**頻率**變高（多一種事件會觸發），建議 qa-tester 在驗收時額外跑一次「2 真人＋2 電腦」的多人局手動 smoke test，確認兩位真人各自收到卡、互不卡住、解完後遊戲能繼續往下走（見下方分派單驗收條件）。這不是要擋修法，是提醒 qa-tester 這次要多測一項既有 mptest／mp2 可能沒直接覆蓋到的情境。

## 需要更新 ADR-001 本文的地方

**是，D5 節第 3 點需要修訂**，因為原文「真人（踩到格子那位）才推 IPO_ANNOUNCE 決策」這句話本身就是這次 bug 的根源設計。已於 `docs/adr/ADR-001-新股抽籤.md` 補上修訂記錄第三條（見下方 diff 摘要），本文件不重複貼整份 ADR，只記錄異動點：

- D5 標題行原文：「`E.openIpo` 生成兩檔 → `E.ipoPollNPC(S)`（電腦玩家立即決定申購，規則見驗收 8）→ `E.ev("IPO_OPENED",…)`」不變（這句沒提跳卡對象，不用改）
- D5 背景描述第 1 點「推一個 `{kind:"IPO_ANNOUNCE"}` 決策給踩到格子的人（真人才推；電腦玩家直接 ACK）」→ 這句已經過時，已在 ADR-001 正文的修訂記錄追加第三條說明現況改為「開盤當下推給全場還在場、沒破產的真人」
- 驗證方式清單新增一項：⑪ 電腦觸發時，桌上其餘真人（非觸發者）也要收到 `IPO_ANNOUNCE`，且互不干擾（多真人局）
