# ADR-001 新股抽籤：雜湊亂數＋預扣帳＋一輪結算

- 對應任務：T-001
- 日期：2026-09-10
- 狀態：**通過**（architect 已審；2026-09-10 修訂：D2 修正 `p.ipoEscrow` 不得參與 `totalAssets`/`netWorth` 運算，理由見下方「修訂記錄」）

## 修訂記錄
- 2026-09-10：architect 審查發現 D2 原文「`p.ipoEscrow` 加回 `totalAssets`」會與 D4 申購分錄（`ASSET +P`）被 `ledger.recompute` 自動加總的部分重複計算，違反憲法第 3 條「複式帳本是唯一真相」。已修正為：`p.ipoEscrow` 僅供 UI 顯示，不參與任何 netWorth／totalAssets 推導，真實來源仍是 ledger 分錄。其餘六條原則（純函數、seeded RNG、資料驅動、feature flag、雙路徑測試、lockstep）審查結果為符合，未修改。
- 2026-09-10（S0 完成後）：①製作人裁示記帳題出題範圍採選項 B——「沒中」「中籤」比照 `dividend` 排除不出題，D4 新增 eduTag `"ipo-settle"` 並要求 S1 把它加進 `DENY` 陣列。②D5-⑤ 文字與 architect 查證結果同步：破產入口確定是 `E.declareBankrupt`，移除「或 S42 遞延入口，名稱待查證」的模糊措辭。

## 決策

### D1 亂數：全部走雜湊，不碰 `util.rand(S)`
新增 `E.ipoRoll(S, tag)`，回傳 [0,1)，演算法照抄 `npc.stableRoll`，輸入字串用 `"ipo|"+tag`。
- 排程：`ipoRoll(S,"sch1")`、`ipoRoll(S,"sch2")`、`ipoRoll(S,"sch2on")`
- 發行：`ipoRoll(S, ipoId+"|"+tier+"|P")`、`"|g"`、`"|list"`
- 抽籤：`ipoRoll(S, ipoId+"|"+tier+"|draw|"+playerId)`

理由：新功能不會讓主亂數流位移，既有的種子測試（例如 s42test）與 simtest 指紋只會受到「抽籤造成的現金變化」影響，不會受到「亂數被多消耗」影響。這條仍然符合憲法第 3-2 條（來源是 `S.seed`，可以重放）。

### D2 State
```json
"ipo": {
  "schedule": [14, 33],
  "fired": [false, false],
  "pending": {
    "id": "IPO1", "fromId": 2, "openedTurn": 14,
    "tiers": {
      "SMALL": { "poolId": "IPO_S07", "name": "…", "P": 88, "g": 0.42, "ref": 124.96, "q": 0.0714 },
      "BIG":   { "poolId": "IPO_B03", "name": "…", "P": 1650, "g": 1.05, "ref": 3382.5, "q": 0.0286 }
    },
    "subs": { "0": ["SMALL"], "2": ["SMALL","BIG"] },
    "declined": { "1": true }
  },
  "history": []
}
```
- `S.ipo` 只在 `E.newGame` 裡、而且 `opts.config.ipoLottery===1` 時才建立；舊存檔沒有 `S.ipo` → 整個機制不作用
- 玩家新增 `p.ipoEscrow`（數字，預設 0），**唯讀顯示欄位，不參與 `ledger.recompute` 任何運算**：
  - `p.ipoEscrow` 只給 UI 顯示「申購預扣款」金額用，數值由 D4 的分錄同步維護（申購時 `+P`、沒中／中籤時歸零）
  - **不得**把 `p.ipoEscrow` 加進 `totalAssets` 或 `netWorth` 的推導（`engineCore.js` 約 63–78 行的 `ledger.recompute`）——D4 的申購分錄（`ASSET ＋P`，refId＝`ipoId+"|"+tier+"|"+pid`）本來就會被 `ledger.recompute` 自動走訪並加總進 `totalAssets`；若再手動疊加 `p.ipoEscrow`，等於同一筆預扣款算兩次，變成一本帳本之外的平行帳，違反憲法第 3 條「複式帳本是唯一真相」
  - 若 UI 需要顯示申購明細（不只是總額），改為直接從 `p.ledger` 依 `eduTags:["ipo"]` 或 refId 前綴 `ipoId+"|"+tier` 篩選、加總顯示，不要再另開 state 欄位參與計算
  - 資料真實來源永遠是 ledger 裡 refId 對應的 ASSET 分錄；`p.ipoEscrow` 只是快取，不得被其他程式碼（紓困額度、排名、破產判定）讀取用於財務判斷

### D3 Action
```json
{ "type": "IPO_SUBSCRIBE", "playerId": 0, "payload": { "ipoId": "IPO1", "tier": "SMALL" } }
{ "type": "IPO_DECLINE",   "playerId": 1, "payload": { "ipoId": "IPO1" } }
```
- 兩者都列入 `E.OFF_TURN_RESPOND`
- reject 碼：`NO_IPO`、`IPO_MISMATCH`、`IPO_DUP`（同一檔重複申購）、`IPO_CASH`、`IPO_TIER`

### D4 帳本
| 事件 | postings | eduTags |
|---|---|---|
| 申購 | CASH −(P＋fee＋notice)；ASSET ＋P（refId＝`ipoId+"|"+tier+"|"+pid`，label「申購預扣款：<名稱>」） | `["ipo"]` |
| 沒中 | CASH ＋(P＋notice)；ASSET −P（同一個 refId） | `["ipo","ipo-settle"]` |
| 中籤 | ASSET −P；CASH ＋listPrice（label「新股上市賣出：<名稱>」） | `["ipo","ipo-settle"]` |

`fee`＝`ipoFee` 0.02、`notice`＝`ipoNoticeFee` 0.05（千元；參考證交所：處理費 20 元不退，中籤通知工本費 50 元未中籤退還）。

**記帳題出題範圍**（S0 查證，見 `docs/reports/T-001-engine-engineer-S0.md`；製作人裁示採選項 B）：「申購」是玩家主動決策，出記帳題；「沒中」「中籤」是抽籤自動結算，比照既有 `dividend` 的作法排除，不出題。做法：`E.buildBookkeeping`（`applyAction.js` 約 4139 行）的 `DENY` 陣列新增 `"ipo-settle"`，讓帶這個 eduTag 的分錄被過濾掉；`"ipo"` 這個 tag 維持不進 DENY，讓「申購」分錄仍可出題。
**備案**：如果 `gate.js` 的 `assetLedgerMismatch` 對「不在 `p.assets` 裡的 ASSET refId」報錯，改成把預扣款放進 `p.assets`，kind 設為 `IPO_ESCROW` 並加 `flags.locked=true`，同時排除所有出售路徑（`E.sellAsset` 有 9 個呼叫點）。**要走備案之前，先回報 architect**，因為這會擴大 ui 的範圍。

### D5 觸發與結算
1. `case "MARKET"`：`S.ipo && !S.ipo.pending` 而且 `E.ipoDue(S)` → `E.openIpo(S,p)`，推一個 `{kind:"IPO_ANNOUNCE"}` 決策給踩到格子的人（真人才推；電腦玩家直接 ACK），然後 `break`，不抽市場卡
2. 保底：`E.beginTurn` 在輪首（`activePlayerIdx` 為第一個未破產玩家時）檢查「排定輪次 +3 < turnNumber 而且還沒觸發」→ 由當前玩家開啟公告
3. `E.openIpo` 生成兩檔 → `E.ipoPollNPC(S)`（電腦玩家立即決定申購，規則見驗收 8）→ `E.ev("IPO_OPENED",…)`
4. 結算：在 `E.beginTurn` 中 S39 集資區塊**之後**，條件比照 `due` 的算法 → `E.settleIpo(S)`：依 `subs` 的 key 做數字排序（**不得**依賴物件插入順序）逐人抽籤 → 過帳 → `E.ev("IPO_SETTLED",{results:[…]})` → `S.ipo.history.push(摘要)`、`pending=null`
5. 破產：`E.declareBankrupt`（`applyAction.js:3632-3636`，architect 已查證確認，非 S42 遞延入口）在清算（`p2pLiquidate`，`:3633` 行）前呼叫 `E.ipoRefundPlayer(S,p)`

## 替代方案與為什麼不選
1. **做成市場牌堆的一張卡**：出現次數會跟人數連動（6 人局約 1.7 次，3 人局不到 1 次），不符「一局 1–2 次」
2. **用 `util.rand(S)`**：每局都會觸發，而且發生在第 8–20 輪，之後的亂數流全部位移，連帶讓寫死種子的測試與 simtest 指紋大面積改變，歸因困難
3. **預扣款不入帳、只扣現金**：申購期間淨值會掉 P，違反鐵律三；股王檔會讓排名在一輪內失真
4. **新增帳戶 ESCROW**：記帳題的帳戶選項沒有這一類，玩家會答不出來、END_TURN 被卡住

## 影響
- 七條原則：純函數 ☑（雜湊）／seeded ☑（來源 S.seed）／ledger ☑（D4）／資料驅動 ☑（D6、D7）／feature flag ☑（`ipoLottery`＋`S.ipo` 存在性）／雙路徑測試 ☑（s45test 同時覆蓋真人與電腦玩家）／lockstep ☑（非回合動作進 actionLog，結算依數字排序）
- 相容：舊存檔不觸發；舊客戶端連進新房會不認得新動作 → 由 network-engineer 確認版本不符時的既有擋法（**UNKNOWN**）
