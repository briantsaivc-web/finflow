## 背景（不重複 engine-engineer 報告全文，只列裁決依據）

engine-engineer 已用 log 證實根因鏈：T-86 情境 (b) 直接把 `S2.turnNumber` 跳到
`maxTurns+1`（跳過 97 輪、不經過逐輪 `beginTurn`）→ `S.ipo.schedule[0]=16` 早已過期未開
→ `EXTEND_GAME` 續攤呼叫 `E.beginTurn(S)`（`applyAction.js:1305`）→ 保底補開段落
（`applyAction.js:4262-4270`，ADR-001 D5-2）條件成立 → `E.openIpo(S,p)`
（`applyAction.js:4639-4650`）→ 同步呼叫 `E.ipoPollNPC(S)`（`applyAction.js:4652-4678`）
→ NPC `playerId=1` 被過帳一筆新股申購款。我已重讀 `applyAction.js:4230-4270`
與 `4638-4678` 逐行核對，engine-engineer 的定位與行號引用**完全正確**，非猜測。

## 裁決

### 問題 1：這算不算「涉及共用結算段落」，需要 architect 裁決？

**算。** engine-engineer 判斷正確，維持停手回報的做法是對的。理由：
`applyAction.js:4262-4270` 與票內明確列出的 `4245-4260` 同屬 `E.beginTurn`
內、對多玩家有現金副作用的區塊，而且是 T-001 剛驗收上線的邏輯，落在票內驗收條件 6
「根因牽涉到 `E.beginTurn` 內與 T-001 新股結算共用的段落」的範圍內，不是
engine-engineer 能自行決定的層級。

### 問題 2：修法方向 —— 裁定 **(c)**，理由如下

先處理「未預期發現 2」的關鍵判斷：**engine-engineer 的懷疑成立。**

我對照 ADR-001 原文 D5 節第 2、3 點：

> 2. 保底：`E.beginTurn` 在輪首（`activePlayerIdx` 為第一個未破產玩家時）檢查
>    「排定輪次 +3 < turnNumber 而且還沒觸發」→ 由當前玩家開啟公告
> 3. `E.openIpo` 生成兩檔 → `E.ipoPollNPC(S)`（電腦玩家立即決定申購……）→ `E.ev("IPO_OPENED",…)`

這是 ADR-001 明文寫死的設計，不是 engine-engineer 誤讀，也不是 T-003 這次程式碼調查
「順便發現」的新行為。這代表：**任何一位玩家的 `beginTurn`**（不限
`EXTEND_GAME`），只要當時 `S.ipo.pending===null` 且排定輪次已過保底寬限
（`ipoGraceTurns`，預設 3 輪），就會在**該玩家的回合起始**同步觸發全桌 NPC
申購判斷。這是 `E.beginTurn` 這個共用函式的固有行為，從 T-001 上線那一刻起就
對所有正常對局成立，只是「每輪都會 check 一次」的日常對局中，保底缺口通常很小
（大多數情況下有人會先踩到 `MARKET` 格觸發，正常觸發走 D5-1，不會累積到需要
保底），因此難以被人工測試或日常遊玩注意到；T-86 情境 (b) 用「一口氣跳 97 輪」
的極端建局方式把這個本來就存在、但發生機率很低的路徑，人為地放大成 100% 必現。

所以：**T-86 情境 (b) 「續攤只能讓當事人一人現金變動」這個斷言，其假設前提
（`E.beginTurn` 只會對當前玩家一人有現金副作用）在 T-001 上線後已經不成立，
不是這次 T-003 調查製造出來的新問題，而是測試斷言沒有跟著 ADR-001 D5-2／D5-3
一起更新。** 這符合 CLAUDE.md 第 5 節「查不到就標 UNKNOWN、不把推論寫成事實」的
反面驗證——這裡我是有 ADR 原文＋程式碼逐行核對兩個獨立證據支持，可以下定論，
不是臆測。

**為什麼不選 (a)：**
`EXTEND_GAME` 續攤時特別跳過保底 IPO 檢查，會讓 `EXTEND_GAME` 的 `beginTurn`
行為與「正常玩家開始一輪」的 `beginTurn` 行為出現分歧——這違背 `E.beginTurn`
作為單一共用回合起始入口的設計初衷，而且是用一個隱藏旗標／特判去掩蓋一個其實
不是 bug 的行為，屬於「改程式遷就測試」，方向錯誤。且對「正常對局中任何人的
`beginTurn` 都可能觸發保底並讓 NPC 同步申購」這個既有現象完全沒有處理到，
只是把 `EXTEND_GAME` 這一個入口特殊化，治標不治本。**不採用。**

**為什麼不選 (b)：**
`E.openIpo` 開盤當下同步呼叫 `E.ipoPollNPC` 是 ADR-001 D5-3 明文、經 architect
審查通過、且 `tests/s45test.js` 已經覆蓋驗證過的設計（ADR「驗證方式」第 5、6 點
明確列了「非回合申購＋reject 碼」「電腦玩家保留水位」）。把它改成「排到下一次
真正輪到 NPC 時才申購」是**推翻一個已經審查通過、正式上線的設計決策**，影響
所有正常對局的 IPO 開盤時序（不只 `EXTEND_GAME`），必須整套重跑
`tests/s45test.js` 十項驗證＋`tests/gate.js`＋`simtest` 指紋比對，而且動機只是
為了遷就一個過時的測試斷言，效益與風險完全不成比例。若真有產品面理由要改
「NPC 何時申購」的時序，應該是另開一張新票走完整的 ADR 修訂流程（產品面評估、
重新設計、製作人核准），不是為了修這張除錯票而順手動。**不採用。**

**採用 (c)：認定現有 engine 行為是 ADR-001 明文設計下的合理行為，修正測試斷言。**
理由已如上：有 ADR 原文＋程式碼雙重佐證，且此舉不需要對已驗收上線的 T-001
機制做任何修改，風險最低、且是唯一「不繞過 CLAUDE.md 第 5 節工作紀律／不生
新 ADR 例外」就能收斂的路徑。

### 問題 3：測試要怎麼改（具體到可直接動手的程度）

**不需要**改動 `tests/s39test.js`／`tests/s45test.js`，因為裁定方向是 (c)、
不修改任何 `src/engine/` 檔案。但仍要求 engine-engineer 在改完測試後，額外
執行一次 `tests/s39test.js`、`tests/s45test.js`（用既有指令，不修改內容）確認
**目前仍是全數通過**，作為「我對 `E.beginTurn` 共用段落的理解沒有誤判」的
交叉驗證證據，寫進回報即可，不必逐項展開分析。

**只改 `src/ui/uiViews.js:1618-1621`**（T-86 S14b 情境 (b) 的最後一段斷言），
其餘情境 (a)(c)(d)(e) 不動。具體改法：

1. **保留**現有的建局方式（`S2.turnNumber=S2.config.maxTurns+1` 直接跳輪次）
   ——不要改成逐輪跑 `endTurn→beginTurn`。理由：(i) 逐輪重放 97 輪需要處理
   擲骰、移動、NPC 決策等大量非本測項關注的路徑，會讓這個測試變得又慢又脆弱，
   且無法保證跑完後 `S.ipo.pending` 一定是 `null`（可能剛好又排到第二檔
   `schedule[1]=43` 卡在 pending 中間狀態），反而引入新的不確定性；(ii) 直接
   跳輪次本身沒有錯，它精準模擬了「時間到強制結算」這個產品情境，問題只出在
   斷言本身寫得過緊，不是建局方式有問題。

2. **把斷言從「數量門檻」改成「白名單集合＋金額交叉驗證」**，寫法如下
   （`r2` 是同一段測試前面已呼叫 `E.apply(...)` 拿到的回傳值，本來就有
   `events` 欄位，`applyAction.js:207/1557` 已確認 `E.apply` 一律回傳
   `{state, events}`）：

```js
// 續攤不是重開：現金水位必須連續。允許變動的只有：
// (1) 接回當事人（player 0，本情境固定，發薪）
// (2) ADR-001 D5-2／D5-3：若續攤這次 beginTurn 剛好觸發 IPO 保底補開，
//     E.openIpo 會同步呼叫 E.ipoPollNPC 讓符合條件的電腦玩家立即申購——
//     這是 T-001 既有設計行為，不是 bug，允許這些玩家的現金也變動，
//     但變動金額必須精確等於「申購款＋手續費＋通知費」，防止真的有
//     其他未預期的 bug 藏在這條路徑裡被誤判為「反正是 IPO 就放行」。
var ipoSubs = r2.events.filter(function(e){
  return e.type==="IPO_SUBSCRIBED" && e.npc===true; });
var allowed = {0:true};
ipoSubs.forEach(function(e){ allowed[e.playerId]=true; });
var cashA=S2.players.map(function(z){return z.cash;});
var badIdx = cashA.map(function(c,i){ return i; }).filter(function(i){
  return cashA[i]!==+cashB.split("|")[i] && !allowed[i]; });
assert(badIdx.length===0,
  "續攤不得重算「當事人＋保底IPO同步申購的電腦玩家」以外的現金，異常玩家 idx="+badIdx.join(","));
ipoSubs.forEach(function(e){
  var before=+cashB.split("|")[e.playerId], after=cashA[e.playerId];
  var expectDelta = -util.r2(e.price + E.cfg(S2,"ipoFee",0.02) + E.cfg(S2,"ipoNoticeFee",0.05));
  assert(Math.abs((after-before)-expectDelta)<1e-6,
    "電腦玩家因保底IPO被動申購的現金變動應等於「申購款＋手續費＋通知費」，playerId="+e.playerId+
    " 實得差額 "+(after-before)+" 期望 "+expectDelta);
});
```

3. `cashB` 的取值方式（`uiViews.js:1611`）不用改，維持 `S2.players.map(...).join("|")`。

4. 跑完後請確認：用種子 8602 這個測項在**目前的 engine 行為下**，
   `ipoSubs` 陣列是否非空（依 engine-engineer 的 log，這裡預期會有
   `playerId=1` 的一筆），藉此讓這段新斷言**實際覆蓋到**「白名單放行且金額
   驗證通過」這條路徑，而不是恰好因為 `ipoSubs` 是空陣列而退化成跟原本
   `<=1` 等價的弱測試。若跑出來 `ipoSubs` 是空的（例如未來 balance 參數
   調整導致觸發條件改變），回報時要註明，不要略過不提。

5. 不需要新增獨立測項覆蓋「AI 對手路徑」——本情境 (b) 本身就同時涵蓋
   當事人（真人玩家 0）與 NPC（`ipoPollNPC` 判斷的電腦玩家）兩條路徑的
   現金變動，符合 CLAUDE.md 第 3 節第 6 條「AI 對手與人類路徑都要測」，
   不必為此另開新測項。

## 問題 3 補充：多人 lockstep 確定性檢查（票內第 4 點要求）

已核對 `E.ipoPollNPC`（`applyAction.js:4652-4678`）：
- 玩家遍歷順序是 `S.players.filter(...)`——固定陣列（建局時就決定順序，非
  `Object.keys` 之類會受物件插入順序影響的寫法），確定性成立。
- 抽籤／發行用 `E.ipoRoll`（雜湊 RNG，來源 `S.seed`），`ipoPollNPC` 本身的
  申購判斷（`q.cash-cost >= reserve`）是純數值比較、SMALL→BIG 固定順序，
  沒有用到任何隨機數，所以「誰會申購」這件事本身是 100% 確定性的（不像
  抽籤結果需要雜湊）。
- 沒有讀 `Date.now()`／`Math.random()`／DOM／全域可變狀態，符合 CLAUDE.md
  第 3 節第 1、2、7 條。

**結論：`E.ipoPollNPC` 在保底開盤時同步執行，不存在額外的非確定性風險**，
與 ADR-001「影響」段落原本標記的「☑ lockstep」評估一致，不需要為此另開
ADR 或追加防護。這點只是確認、不是新裁決，供 engine-engineer 回報時引用即可。
