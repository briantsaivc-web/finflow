## 零、先講一件事：其中三個回報是同一條根因鏈

回報的「1. 中斷」「2. 某玩家可借款狀況不一致」「5. 合資邀請時有 bug」不是三個獨立問題，是同一條線上的三個症狀。那張卡住面板把證據都印出來了：

```
輪次 11　玩家 Brian　階段 DECISION　待決 BUY（OPS_BZ16）
待決屬於 Brian（座位 2）　我是座位 0
懸置合資 true
例外：多人局動作連續被拒：NO_CAPACITY
```

`NO_CAPACITY` 全檔只有一個出處——`TAKE_LOAN` 裡的 `if(amt2<=0) return reject("NO_CAPACITY")`。往回追有兩個地方會送出金額對不上的 `TAKE_LOAN`：

### 根因 A：借款面板寫死座位 0

```js
ui.showLoanDialog = function(){
  var S=ui.S, p=S.players[0];        // ← 寫死
```

單機時 `myId()` 剛好就是 0，所以從來沒被發現。多人局座位 1／2 打開借款面板，讀到的是**座位 0 的收入、負債與額度**——右欄標題列的「借款空間」用的是你自己（`E.creditCapacity(S,p)`），面板裡的「尚可借」卻是別人的，兩個數字自然對不起來（你截到的 1,150,930 vs 174,270）。更糟的是按下去送出的是 `TAKE_LOAN{playerId: 你的座位, amount: 照別人額度算的金額}`，引擎拿你的額度去比 → `NO_CAPACITY`。

**修法**：`S.players[ui.myId()]`。

### 根因 B：合資邀約的借款鈕用舊值重送、而且不管成敗都說「已借入」

```js
var take = Math.min(cap, gap);        // 算一次就存在 closure 裡
b.onclick = function(){
  ui.dispatch({type:"TAKE_LOAN", ..., {amount:take}});
  ui.toast("已借入 "+M(take)+"...", "good");   // ← 不看引擎接不接受
};
```

按鈕按完**不重畫、也不關面板**。所以：第一次按借到了 → 額度歸零 → 第二次按送的還是同一個舊 `take` → `NO_CAPACITY`。而畫面上仍然跳「已借入 895,000」，玩家以為沒生效就再按 → 第三次觸發卡住面板。

**修法**：每次按之前重算 `cap/gap/take`、按完重畫（額度用完就自己停用）、只有現金真的變了才說借到了。

### 根因 C：那個卡住面板本來就不該跳

```js
ui.mp._rejects=(ui.mp._rejects||0)+1;
if(ui.mp._rejects>=3) ui.showStuck(...)     // 玩家自己按的也算
```

玩家手動點的動作被拒三次就跳「**這是程式的問題，不是你操作錯了**」——但額度不夠而被拒，是規則正常運作，不是程式壞了。

**修法**：只有電腦代跑的迴圈（`mpAfter`）連續推不動才算卡住；玩家手動的被拒改成一句看得懂的話。順便把被拒原因翻成人話——玩家看到 `NO_CAPACITY` 只會更慌：

> 信用額度不足，借不到這個金額（額度＝月收入 × 倍數 − 現有無擔保負債）

## 一、另外兩項

### 4. 借款拉桿拉不到滿——算給你看

```js
rng.max  = Math.round(cap);              // 174
rng.step = Math.max(1, Math.round(cap/20));   // round(8.71) = 9
```

`max` 不是 `step` 的整數倍，拉到底只能到 `floor(174/9)×9 = 171`。所以面板寫「尚可借 174,270」，拉到底卻是 **171,000**——跟你截到的數字完全吻合。玩家只好借第二次補尾數。

**修法**：`step` 固定 1（＝1,000 元，刻度乾淨），`max` 用 `Math.floor(cap)`，另外加一顆**「借滿 X」**直接送精確的 `cap`，一次到位。

### 3. 人生商城：別人的回合只能看、同一輪只能買一次

兩個問題各有各的成因：

**（a）非回合可買**是 S14a 的決定（「先只開放不影響別人的動作——還款、設定定期定額、逛商城買東西」）。你現在要改成只能看，所以把 `MALL_BUY` 從固定白名單改成看開關：

```js
E.offTurnSelfOk = function(S, type){
  if(E.OFF_TURN_SELF_BASE[type]) return true;
  if(type==="MALL_BUY") return !!E.cfg(S,"mallOffTurnBuy");   // 預設 0
  return false;
};
```

畫面同步：商城**照樣打得開**（別人回合可以先研究），但每一件的買鈕停用，理由寫明「現在是別人的回合——可以先看，買東西要等輪到你」。

**（b）同一輪買兩次**的成因是計數只重置當前玩家：

```js
E.endTurn = function(S){
  var p=E.activePlayer(S);
  ... p.mallBoughtThisTurn = 0;      // 只歸零「剛打完的那個人」
```

非回合購買開放之後就漏了：你在別人的回合買一次 → 自己的回合結束時計數被歸零 → 再到下一位的回合又買一次。你截的第 2 輪正是這個順序（先買「AI 程式設計大賽」，自己的回合跑完，再買「大專排球聯賽」）。

**修法**：改成每一輪結束時 `E.onRoundEnd` 把**全員**歸零，語意才真的是「同一輪只能買 `mallPerTurn` 次」。

兩項都掛在開關後面（`mallOffTurnBuy`／`mallResetPerRound`），關掉就完整回到 S18 的行為。

## 二、一個必須說清楚的驗證限制

平衡指紋跑出來 **S19 預設與 S18 逐項相同**。這**不是**「改動安全」的證據，而是「模擬看不到這個改動」的證據。我另外量了 200 局：

| | 商城購買總次數 |
|---|---|
| S19 預設 | 669 |
| 開關回舊行為 | 669 |

**完全一樣**——因為 NPC 只在自己的回合被驅動，本來就不會非回合購買，每輪上限也就從來沒被繞過。這正是設計鐵律第 5 條說的「NPC 跑不到的路徑等於沒被測到」。

所以這一批的真正覆蓋來自 `s19test.js`（直接呼叫引擎與 UI 函式，繞過 NPC）與你的實測，不是來自 500 局模擬。**請特別複驗**：非回合的商城買鈕是不是全部停用、同一輪能不能買第二次、下一輪有沒有恢復。
