# FinFlow S25d 變更說明——dropStudy 多人連線永久錯位修復（v2.32.3-S25d）

## 一、要修什麼

你實測回報:「我正修一門課,後抽到經營線上課程的機會,所以我選擇放棄修到一半的課,結果死當」——畫面卡在「把這些變動放進正確的欄位」記帳分類小遊戲,按鈕全部停在「狀態已更新，請再操作一次」,之後怎麼點都一樣,無法再進行任何操作。

## 二、根因

這是一個**只有多人連線模式才會發生**的 bug,單人模式完全測不出來。

多人連線靠一份共用的「動作紀錄」(`S.actionLog`)對齊每個玩家的畫面:你送出一個動作前,會先在本機算「這應該是紀錄的第幾筆(`seq`)」,送給共用紀錄比對;對不上就會顯示「狀態已更新，請再操作一次」,並自動補上你漏看的部分後讓你重新操作一次——這個提示本身平常是正常機制,不是 bug。

問題出在「開始經營數位資產」這張決策卡裡的「放棄目前正在修的課」選項:它內部會**再呼叫一次**完整的「放棄技能」動作(`E.apply(...ABANDON_SKILL...)`),而不是只執行放棄技能的效果。這一次「動作裡面又包一次完整動作」,會讓引擎在处理同一筆「決定」的過程中,對 `S.actionLog` 多推一筆你送出動作時完全沒算到的「憑空」紀錄。

單人模式沒人在比對紀錄筆數,完全看不出差異。但只要你在多人連線裡點過一次「放棄修課,改去經營數位資產」,你本機算出來的紀錄筆數就從那一刻起,永遠比共用紀錄少算一筆——之後每一個動作送出去都會被判定「筆數對不上」,永遠卡在「狀態已更新，請再操作一次」,而且系統的自動補正機制本身沒辦法修好這個「本機算法本身就固定少算一筆」的根因,所以是永久卡死,不是重試幾次就能過去的暫時性訊息。

全程式碼掃過一輪,這種「一個動作內部再包一次完整動作」的寫法只出現在這一處。

## 三、修法

把「放棄修課」原本會做的事(退部分學費、停月費、記一筆放棄紀錄、清空進修狀態)抽成一個獨立的效果函式(`E.applyAbandonSkill`),不再包在一個完整、會自己往紀錄裡推一筆的「動作」裡。

- 玩家主動按「放棄進修」時:先確認這是一筆合法動作,紀錄一筆,再呼叫這個效果函式——行為跟以前完全一樣。
- 「開始經營數位資產」決策卡裡的「放棄修課」選項:直接呼叫這個效果函式做完該做的事,不再多包一層動作、不會再多推那筆憑空紀錄。

兩邊看到的遊戲效果(退費、停月費、進修狀態清空)完全一樣,差別只在「這件事算不算一筆獨立的、要送去跟其他玩家對齊的動作」——現在只有你主動按「放棄進修」按鈕才算一筆,透過「開始經營數位資產」順手放棄修課只算開始經營這一筆,不會被多算。

## 四、測試與驗證

- 新增自測 T-87:模擬一個玩家正在進修、又抽到數位資產機會、選擇「放棄修課」,驗證這整個「決定」動作在 `S.actionLog` 裡只留下一筆紀錄(不是兩筆),且放棄修課與開始經營的效果都正確發生。**已用「先移除修復再跑測試」的方式確認這條測試在修復前真的會失敗**(一筆 DECIDE 動作只該在 actionLog 留一筆紀錄,實得 2 筆——跟原本分析的「多推一筆」完全吻合),不是空跑一次就通過的假測試。
- 既有 T-72(抽到數位資產卡時可以放棄進修來接)刻意用不同呼叫方式繞過了「決定」動作本身的紀錄流程,所以之前一直沒抓到這個 bug——T-87 特意從玩家實際操作的路徑(送出一筆 DECIDE 動作)去驗證,才補上這個測試死角。
