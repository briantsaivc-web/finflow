## 1. 面板跑出 `<b class='gold'>`、`<br>` 字面標籤

### 根因
UI 的建構函式 `el(tag, cls, txt)` 一律走 `textContent`，四處把排版標籤直接塞進 `txt`，於是標籤被當成文字印出來。

### 涉及的四處（全檔掃描結果，非只有截圖那兩處）
| 行 | 面板 | 內容 |
|---|---|---|
| L6479 | 現金不足（破產） | `<b class='gold'>還差 32,540</b>`、`<b>只要補得上缺口就好…</b>` |
| L10628 | 借款 | `年利率 9.50%<br>目前負債總額 …` |
| L6162 | 帳上獲利提示 | `<b>事先想好在什麼條件下要下車</b>` |
| L6780 | 買股票 | `標的：<b>台積電</b>` |

截圖只看得到前兩處，另外兩處是同一個病灶，只是還沒被踩到。

### 修法：不是逐處改字串，是把病灶收斂在 `el()`
逐處改只是把四個症狀藏起來，第五處遲早會再出現。改成在 `el()` 統一判斷：

- **純排版標籤**（`b / i / u / br / em / small / strong / span`，可帶 `class`）→ 走 `innerHTML`，正常排版
- **其餘一律當純文字** → `script`、`img onerror`、`on*` 事件、`a href`、`iframe`、`style` 全部原樣顯示為文字，進不了 DOM

判斷函式 `ui.isSafeMarkup(s)` 是純函式，可以被測試直接驗，不需要 DOM。
（正規表示式的交替分支首字元互斥 `[^<]` vs `<`，是線性掃描，不會回溯爆炸。）

## 2. 踩到「人生」格改成二選一

### 做法
新增 `PICK_LIFE` 決策：踩到人生格抽兩張，玩家選一件面對。

**關鍵設計**：`SKILL_GATE`（書到用時）卡會直接標示 **「✅ 你接得住：已具備 XXX」** 或 **「⚠️ 你沒有準備：需要 XXX」**。
有準備的人可以挑自己接得住的那件事先處理——這正是「不努力、不準備，機會來了就會錯失」的正面。

### 但第一版量出來難度崩了，所以我改了設計

第一版是「選一件，另一件進棄牌堆」（跟小機會完全一樣）。5 個 seed 集 × 60 局量測：

| 指標 | S3 | S3b 第一版 | 判定 |
|---|---|---|---|
| **破產率** | 5.9%（3.9~8.9） | **1.0%（0.6~1.7）** | **區間完全不重疊，−83%** |
| 進圈率 | 44.6% | 54.1% | +21% |

**這變成「免費閃避壞事」，跟你自己的設計主張「為種下的因承受其後果」是反的。**

**改法：選的是順序，不是逃避。** 沒選的那件記在玩家身上（`deferredLifeId`），
**下次踩到人生格時直接找上門**，不再給你二選一。側欄會常駐提示「還擱著一件事：〈標題〉」。

這樣做保住了三件事：
1. 你要的二選一還在
2. 事件總量沒有減少 → 難度回到原位
3. **策略價值反而更好**：你爭取到的是「時間差」——先處理接得住的那件，另一件延後到你可能已經學會那項技能之後。準備買到的是選擇權，不是豁免權。

| 指標 | S3 | S3b 定案 | 判定 |
|---|---|---|---|
| 局長中位 | 68.6（66~71） | 69.2（66~71） | +1%，區間重疊 ✓ |
| 進圈率 | 44.6%（41.1~46.7） | 46.1%（42.2~50） | +3%，區間重疊 ✓ |
| 跌回率 | 15.5%（11.4~21.6） | 15.3%（9.6~19.7） | −1%，區間重疊 ✓ |
| 破產率 | 5.9%（3.9~8.9） | 5.2%（3.9~6.7） | −12%，區間重疊 ✓ |

60 局實測：二選一觸發 833 次、擱置 833 件、**擱置後真的被追上 729 次（88%）**，其餘 12% 是收局時還掛在身上。

### 副作用（已量測，屬預期）
技能錯失從 66 次降到 49 次（−26%）。因為玩家會挑自己接得住的那件先處理——這是機制本來就要達成的效果，不是漏洞。兌現:錯失 = 208:49，錯失仍佔兩成，教學意義保留。

### 開關
新增 `lifeDualChoice`（設定面板「機會」組），與 `oppDualChoice` 同進退：**標準難度以上開啟，新手難度關閉**。設為 0 時逐位元回到 S3 行為（12/12 局驗證）。

## 4. 未預期發現

**修補腳本又出現一次「中途 assert 失敗 → 整支腳本在寫檔前中止」**：這次是我把「應該加在 HTML 上的錨點」誤用成「改修補腳本自己的文字」，四項修改全部沒落地。因為寫檔在最後一行，產出檔沒被污染，當場察覺並重做。與 S3 那次同源，屬同一類。

**已固化的做法**：每次改完修補腳本，一律從**輸出檔**實際抽查錨點是否存在（本次抽查 10 個關鍵字全部命中），不以「腳本執行成功」當作證據。
