## 1. NEW-01 新創「跟投」重複入帳（P0，財務真值）

### 問題
跟投（follow-on）的出資額被記了兩次 ASSET：一次是「跟投出資」本身，一次是隨後的「估值更新」（`post × equityPct` 已經完整含了這筆增資）。公司倒閉時的沖銷用的是 `-a.marketValue`，只沖得掉市值那一份，**多記的出資額永遠留在帳上**。

實測復現（seed 118446、Player 2、資產 A_1357）：
```
T56 投資新創    ASSET +360.00
T59 跟投        ASSET  +89.25  ← 多的那一筆
T59 估值更新    ASSET +300.45
T63 估值下修    ASSET -363.25
T65 新創倒閉    ASSET -297.20
                ───────────
          分錄餘額 +89.25    實際市值 0
```

1,400 個玩家終局中 23 人（1.6%）中招，**全部是虛增**，累計 2,878.77、單筆最大 695.55。這筆錢會灌進 `derived.netWorth` → 財報、排行榜、勝負判定、模擬器的「淨值中位」。

### 修改
- `E.resolveDecision` / `case "FOLLOW_ON"`：刪除多餘的 `ASSET +inv` 分錄，出資只走 CASH
- `M.registry.M3.onPayday`（NPC 跟投路徑）：同上
- `costBasis` 兩處都維持 `+inv` 不變（成本基礎本來就該含跟投）

### 為什麼原本 72 條自測抓不到
- **T-03「分錄即真相」**只驗 `netWorth = cash + totalAssets − totalLiabilities`。這條恆等式是 `ledger.recompute` 的定義本身，**恆成立、驗不出東西**。
- **T-06「股權稀釋數學」**只跑了 `"pass"`（不跟投）分支，**含 bug 的 `"follow"` 分支從沒被測過**。

### 新增守門
**T-73 資產分錄與市值逐項對帳**：30 局 × 3 人，每一項資產的 ASSET 分錄餘額必須等於它的 `marketValue`。

## 3. NEW-03 貸款繳清後資產仍指著已消滅的負債（未預期發現）

> 這一項不在你交辦的清單裡，是驗證過程中撞到的。依規矩明列，不靜默處理。

### 問題
`E.repay`、房貸攤還結清、賣資產時清償連結負債——三處都把 liability 從 `p.liabilities` 移除，但**沒有清掉資產的 `a.linkedLiabilityId`**。該資產從此永遠被視為「抵押中」：

- `PROPOSE_TRADE` → `reject("MORTGAGED")`：**房貸繳清的房子永遠不能轉讓給別人**
- 廣播轉讓的 `sellable` 過濾 → 該資產不出現
- `sell_half`（賣一半）→ 被擋
- 融資部位判定 `marg` → 誤判

1,000 局／3,250 位玩家中出現 1 次（0.03%）。**在改動前的原檔跑同一批 seed 也出現同一筆**，確認是既有問題、非本次引入。

### 修改
新增 `E.unlinkLiability(p, lid)`，在上述三個負債移除點呼叫。

### 新增守門
**T-81 貸款結清後資產不得還指著不存在的負債**：全額提前清償後 `linkedLiabilityId` 必須為 null，且該資產可以被 `PROPOSE_TRADE` 接受。

## 4. FF-001／FF-002 模擬器統計（P0）

### 問題
`ns.simui.show()` 分批執行（每批 20 局）後用摘要相加：
```js
s.freeRate=(s.freeRate+o.freeRate)/2;          // 未加權連續平均 → 指數加權到最後一批
s.bankruptRate=(s.bankruptRate+o.bankruptRate)/2;
// p10 / p90 / medianNetWorth 從第二批起完全沒被更新
```
表頭寫「200 局」，**P10／P90／淨值中位其實只來自最前面 20 局**。

修改前實測（200 局，UI 顯示 vs 同批 seeds 全樣本真值）：

| 性格 | 自由率 | 破產率 | 中位自由輪 | P90 | 淨值中位 |
|---|---|---|---|---|---|
| NPC_SAFE | 53.4% / **56.5%** | 4.1% / **7.0%** | 49 / **43** | 57 / **63** | 1,512 / **1,266** |
| NPC_LEVER | 86.5% / 86.0% | 1.3% / **0.5%** | 38 / 37 | 52 / **55** | 1,711 / **1,839** |
| NPC_VC | 87.3% / 87.5% | 0.0% / 0.0% | 40 / 41 | 62 / **59** | 2,394 / 2,371 |

保守型的破產率被**低估 42%**、淨值中位被**高估 19%**——拿這張表調參，結論會錯。

### 修改
- 新增 `ns.sim.stats`：`median` / `percentile` / `emptyBucket` / `mergeBucket` / `summarize`，**全檔只有這一份 percentile 定義**（`ns.sim.run` 與 `ns.simui` 共用）
- `ns.sim.run` 改為額外回傳 `raw`（每個性格的原始樣本）、`invalid`、`validGames`；`summary` 保留以維持既有呼叫端相容
- `ns.simui.show` 改為**累加原始樣本**，全部批次跑完才算一次摘要
- **FF-002**：`ns.sim.playOne` 回傳前寫入 `S.simStatus`（`valid` / `reason` / `actions` / `seed` / 卡住時的 phase、decisionQueue 長度等除錯欄位）；`run()` 把 invalid 的局排除在分母外，UI 另行顯示「有效 N 局／異常 M 局」與 seed

> **修正 Gemini 的驗收條件**：它的 T-SIM-01 要求「200 局一次跑完」與「20 局 × 10 批」結果完全一致。這做不到——`ns.sim.run` 的 seed 是 `seedBase + g*7919`，而 simui 每批把 `seedBase` 換成 `1+done*131`，**兩種跑法用的是不同的 seed 集合**。正確的驗收是「批次合併後的摘要 == 用同一批 seeds 的全樣本摘要」，本次即以此驗證。

> **FF-002 的實測事實**：1,000 局跑下來 `guard` 從未逼近上限（最大 1,019／上限 6,000，5.9 倍餘裕），異常局 0。這是安全網，不是在修一個正在發生的問題。

### 新增守門
- **T-76 批次合併必須等於全樣本一次算**：40 局分 10 一批，七項統計量與全樣本**逐位元一致**；另驗加權（10 局 10% ＋ 90 局 90% ＝ 82%，不是 50%）與 percentile 定義單一

## 5. FF-003 多人 UI 把 Player 0 當成「我」（P1）
### ── 同時解掉實測回饋的兩個「嚴重 bug」⑤⑥

`ui.myId()` 全檔已用 140 次，遷移大致完成，但殘留 7 處寫死 0 號座位。其中一處是**你回報的兩個嚴重 bug 的共同根因**：

```js
var isMe = p.id===0;                                  // ← 舊
var canAct = isMe && S.activePlayerIdx===ui.myId() && ...
```

`ui.renderSheet` 裡，**辭職進入自由圈** 與 **📖 進修（自己找資源）** 兩顆按鈕都掛在 `isMe && canAct` 底下。多人局中座位 1 以上的玩家看自己的財報時 `isMe` 恆為 false，於是：

- ⑤ **符合自由圈條件卻沒有進入按鈕** → 按鈕根本沒被 render
- ⑥ **［進修］選項沒出來** → 同上
- 附帶：畫面還會顯示「👁 檢視他人財報中」，而且賣資產／還款等行內按鈕也全部停用

三人局裡有兩個人整局都是這個狀態。

### 全部 7 處修改

| 位置 | 症狀 |
|---|---|
| `ui.renderSheet` `isMe` | **上述兩個嚴重 bug** ＋ 財報所有操作停用 |
| `ui.showMarginCallLesson` | 斷頭教室標題張冠李戴 |
| `RATE_REVIEW` 公告 | 播的是 0 號的月付變動 |
| `RATE_REVIEW` toast | 同上 |
| 結算排行榜高亮 | 高亮錯人 |
| 結算排行榜「（你）」 | 標錯人 |
| 戰報分頁 ＋ 預設明細 | 預設打開 0 號的明細 |

另外順手修掉側欄的 `你的回合`——舊碼只看 `isNPC`，三人真人局中**每個人的回合都會顯示「你的回合」**；現在只有自己顯示「你的回合」，別人顯示「行動中」。

`ns.selftest` 內的 `players[0]` 全部保留（單機 fixture，合法）。

### 新增守門
**T-75 非零號座位的「你」也要是自己**：`seat=2` 時 `myId` / `myP` 正確，且 `renderSheet` 與斷頭教室的原始碼不得再出現寫死的 `p.id===0`。

## 6. FF-004 建房競態 ＋ 房號改 4 碼

### 問題
`readRoom → 檢查 → createRoom` 三步非原子，且 `FirebaseAdapter.createRoom` 用的是 `set()`——**直接覆蓋**。房號只有 00–99 共 100 個，10 間活房同時在線時新房撞號機率就到 10%。撞上就是把別人的 lobby／log 整個清掉的**靜默資料遺失**。

### 修改
- 房號 **2 碼 → 4 碼**（`ROOM_CODE_LEN = 4`，0000–9999，零補齊）；入房輸入框 `maxLength` 與驗證同步改為 4 碼
- TTL 抽成常數 `ROOM_TTL_MS`（原本 `24*3600*1000` 寫死在建房流程裡）＋ `isRoomExpired(room)`
- `FirebaseAdapter.createRoom` 改用 **`runTransaction`**：只有房號空著或該房已過期才寫得進去，`committed === true` 才算建房成功
- `LocalAdapter.createRoom` 加同樣的存在性把關（同步 read→check→write）
- 建房流程改看 `createRoom` 的回傳值：被搶先占走就換一個號重試（最多 30 次）

### 新增守門
**T-80 房號 4 碼且建房不得覆蓋活房**：房號格式與分散度、活房不可回收、過期房可回收。

### ⚠ 限制聲明（UNKNOWN）
沙盒**無法實連 Firebase**（網路白名單，且需你的真金鑰）。Firebase 路徑只做了靜態改寫與邏輯驗證，**未實連驗證**。LocalAdapter 路徑已用三分頁真跑過。
**上線前請在你本機做**：兩台裝置同時建房只有一個成功、過期房可回收、重連 replay 正確。

## 8. 實測② 人生商城可無限重刷幸福感（平衡破口）

### 問題
商城有一批商品**沒有 `oncePerGame`、沒有效期旗標、沒有冷卻**，CP 值極高：

| 商品 | 一次性成本 | 幸福感 |
|---|---|---|
| ML_CMP5 大專排球聯賽（社會組） | 6 | **+2** |
| ML_VIR3 公益定期捐款 | 6 | **+2** |
| ML_CMP1 報名城市馬拉松 | 8 | **+2** |
| ML_VIR4 孩子的才藝課 | 8 | **+2** |
| ML_CMP4 AI 程式設計大賽 | 10 | **+2** |

`mallPerTurn = 1`，一局約 50 輪 → 同一張卡可以刷 50 次，花 300 換 **100 點幸福感**。而勝利門檻 `winWellbeingMin` 只要 10，且 `blessingStep = 10`——幸福感高水位每跨 10 點就送一次盲盒抽獎（20% 夢想進度 +1、15% 現金紅包 50–150、25% 品格 +1）。**這是一條會自我循環的經濟破口。**

### 修改（兩層，套用到全部商城商品，規則單一可解釋）
1. **幸福感邊際遞減**：新增 `E.mallJoyFor(S,p,it)`——同一項商品第 N 次購買的幸福感 = `floor(原值 × decay^(N−1))`。預設 `mallRepeatJoyDecay = 0.5` → joy 2 的卡：**2 → 1 → 0 → 0…**
2. **重購冷卻**：新增 `E.mallCooldownLeft(S,p,it)`，預設 `mallRepeatCooldown = 3` 輪。`MALL_BUY` 在引擎層 `reject("MALL_COOLDOWN")`，UI 灰化只是提示
3. **現金支出不遞減**——遞減的是幸福感不是價格，這正好是「重複消費的邊際效用遞減」的教學點
4. 商城卡片直接寫出「這一次實際能拿到多少」：`幸福感 +1（原 +2，第 2 次）`，以及「剛買過，再過 N 輪才能重複購買」

> 進修（`oncePerGame`）、保險（`insured` / `propInsured` 旗標）、年約（`flag` 效期）本來就有各自的把關，**行為不變**。

新增旋鈕：`mallRepeatJoyDecay`（0–1，預設 0.5，1 為不遞減）、`mallRepeatCooldown`（0–12 輪，預設 3，0 為不限制），兩者都在開發者面板「商城」分組、標 `hot`。

### 新增守門
**T-78 重複購買幸福感遞減且有冷卻**：自動找出一張可重複購買的高 CP 值商品，驗證 `2 → 1 → 0`、冷卻期內被引擎擋下（理由必須是 `MALL_COOLDOWN`）、錢照付。

## 10. 實測⑦ 玩家偶而某一輪被自動跳過

### 誠實的結論：一半是既有機制、一半是碼錯

**（a）機制面 —— 這不是 bug，但介面沒講清楚。**
200 局實測，停走事件共 3,337 次（平均每局 16.7 次），來源分布：

| 來源 | 次數 |
|---|---|
| 失業（LAYOFF 格） | 1,459 |
| 照顧生病的家人 | 97 |
| 父母醫療陪同請假 | 76 |
| 臥床復健 / 入院治療 | 53 |
| 求職空窗 | 26 |
| 跌回內圈 | 16 |
| 會計師考試放榜季 | 5 |

停走是**設計內的機制**（失業、傷病、破產脫困、跌回內圈都會停走），但原本輪到你被跳過時只丟一句 `ui.announce("XXX 這回合停走")` 的短暫橫幅——**沒說為什麼、也沒說還要停幾輪**，玩家自然會覺得是 bug。

**（b）碼錯 —— 這個是真的。**
`E.applyEffects` 的 `switch(ef.op)` 裡有**兩個同名的 `case "SKIP_TURNS"`**：
```js
case "SKIP_TURNS": ... t.skippedTurns += (ef.turns||1);  ... break;   // 有效
...
case "SKIP_TURNS": ... t.skippedTurns += (ef.n||1);      ... break;   // 死碼，永遠到不了
```
JavaScript 的重複 case 標籤合法但第二個永遠不會執行。現有內容裡有 3 張卡寫的是 `{"n": 1}`——湊巧值都是 1 所以看不出來，但**任何一張寫 `{"n": 2}` 的新卡都會被靜默降成停走 1 輪**。

### 修改
1. 合併成單一 case，`turns` 與 `n` 兩種寫法都接受
2. 新增 `p.skipReason`，在**全部五個增量點**記下原因：SKIP_TURNS 卡（用卡片 label）、失業、商城／人生卡的 `skipTurns`、破產脫困、跌回內圈／自願重返、走完破產程序
3. `E.beginTurn` 的 `TURN_SKIPPED` 事件改為帶 `reason` 與 `remaining`
4. UI 改成：公告寫「**小美 這回合停走（失業，正在找下一份工作），之後還要停 1 輪**」，當事人另收一則 5.2 秒的 toast

### 新增守門
**T-79 停走：原因與剩餘輪數要帶得出來**：`n:2` 與 `turns:3` 兩種寫法都要吃到正確輪數、要記下原因、事件要帶得出 `reason` 與 `remaining`。
